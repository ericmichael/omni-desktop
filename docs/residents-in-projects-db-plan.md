# Residents in projects-db — Durable Agent Data as First-Class World State

> Status: **IMPLEMENTED** 2026-07-23 (all four slices). Deviations from the
> plan below, decided during implementation:
>
> - **Write-through cache, not async accessors.** The manager keeps its reads
>   synchronous (speech-tool fulfillment returns results inline), so it holds
>   an in-memory cache of the durable data (the ProjectManager idiom) and
>   persists through a serialized chain. Consequence: the manager is the id
>   authority — `appendResidentMessage`/`addResidentAlarm` take complete rows
>   with caller-assigned ids instead of returning DB-generated ones.
> - **The store→db migration lives inside the manager's hydrate()** (not a
>   separate boot function) — one ordering point, both entry points get it
>   for free. The legacy `projectId` / `{id,text}`-memory migrations folded
>   into it and died as separate steps.
> - **Snapshot mirrors come from the manager's cache**
>   (`getDurableSnapshot()`, composed over `ProjectManager.getStoreSnapshot()`
>   in both entry points), not from repo reads in `buildStoreSnapshot` — the
>   cache is current before the persist lands.
> - **Pg message/alarm ids are `INTEGER GENERATED BY DEFAULT AS IDENTITY`**,
>   not BIGSERIAL (node-pg returns int8 as string; the row types share the
>   SQLite number shape). Ids are caller-assigned anyway.
> - **v16 also relaxes `ticket_comments.author`**: the original schema had
>   `CHECK(author IN ('agent','human'))`, which principal stamping violates —
>   SQLite rebuilds the table (v14 pattern), Pg drops the constraint.
> - The store schema keeps loose (typeless) entries for the five migrated
>   keys instead of dropping them, so a pre-fold store loads cleanly for the
>   one-shot migration.

## Summary

Move the resident agents' durable data — roster/personas, earned memories,
channels + message log, alarms — out of electron-store keys and into
`packages/projects-db`, alongside projects/tickets/pages/inbox. Make residents
**principals**: directory entries the assignee roster can list, an identity
MCP sessions can carry (`agent:<rosterId>`), and a wakeup target when a ticket
is assigned to them. The wakeup/session **runtime** (queues, budgets, cursors,
park/unpark, watcher sockets) stays in `ResidentAgentManager` unchanged.

Why: `omni-projects` is already the shared world model (work graph, pages,
inbox, org directory) with the only local/cloud dual backend in the codebase
(SQLite repo ↔ RLS-scoped Postgres). The resident layer's durable half is the
same species of data sitting in a weaker store — no cloud parity, no
change-seq, no attributability. Folding it in closes three known gaps at the
data layer: assign-to-agent in the UI, residents authenticating as themselves
against MCP, and assignment wakeups.

Lockstep change, no compat shims (repo convention). Out of scope: exposing
channel/memory MCP tools to sandboxes, renaming the `omni-projects` server
label, model tiering. Runtime state (`residentMorningBeats`, thread cursors,
DM budgets) stays where it is.

## 1. Schema (packages/projects-db)

**SQLite — next migration (v16).** ISO timestamps via `toIso`/`fromIso`,
JSON-in-TEXT for arrays, matching existing tables:

```sql
CREATE TABLE resident_agents (
  id            TEXT PRIMARY KEY,          -- slug; process id agent:<id>
  name          TEXT NOT NULL,
  role          TEXT NOT NULL,
  persona_text  TEXT NOT NULL,
  profile_name  TEXT,
  project_ids   TEXT NOT NULL DEFAULT '[]',-- JSON string[]
  morning_hour  INTEGER,                   -- NULL = beat disabled
  enabled       INTEGER NOT NULL DEFAULT 1,
  created_at    TEXT NOT NULL
);
CREATE TABLE resident_memories (
  agent_id  TEXT NOT NULL REFERENCES resident_agents(id) ON DELETE CASCADE,
  key       TEXT NOT NULL,                 -- remember/forget upsert key
  text      TEXT NOT NULL,
  at        TEXT NOT NULL,
  PRIMARY KEY (agent_id, key)
);
CREATE TABLE resident_channels (           -- named channel defs only;
  id          TEXT PRIMARY KEY,            -- team/system/user/dm:* stay virtual
  description TEXT,
  members     TEXT,                        -- JSON string[]; NULL = open
  created_at  TEXT NOT NULL
);
CREATE TABLE resident_messages (
  id        INTEGER PRIMARY KEY AUTOINCREMENT,
  channel   TEXT NOT NULL,                 -- 'team' | def id | 'dm:a:b' | 'system'
  from_id   TEXT NOT NULL,                 -- 'user' | 'system' | roster id
  from_name TEXT,
  text      TEXT NOT NULL,
  at        TEXT NOT NULL,
  reply_to  INTEGER                        -- root message id (pre-normalized)
);
CREATE INDEX idx_resident_messages_channel ON resident_messages(channel, id);
CREATE TABLE resident_alarms (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  agent_id   TEXT NOT NULL REFERENCES resident_agents(id) ON DELETE CASCADE,
  at         TEXT NOT NULL,
  note       TEXT NOT NULL,
  created_at TEXT NOT NULL
);
```

**Type normalization (lockstep, shared/types.ts + manager):**

- `ResidentAgent.morningHour` becomes `number | null` — the "absent = default
  8" case is materialized to `8` during migration; `null` = disabled. The
  `?? DEFAULT_MORNING_HOUR` fallbacks in `resident-agent.ts` are deleted.
- `ResidentAlarm.id` becomes globally unique (autoincrement) instead of
  per-agent; the manager's alarm bookkeeping keys on the global id.
- Message `from` → `from_id` in rows only; launcher-facing types unchanged.

**Postgres (`pg/schema.ts`):** the same five tables with the standard
`tenant_id TEXT NOT NULL` column, per-table tenant index, and the
`tenant_isolation` RLS policy — copy the existing table pattern exactly.
`resident_messages` uses `BIGSERIAL`; uniqueness is
`(tenant_id, id)` for `resident_agents`/`resident_channels`.

## 2. Repo interface (`IProjectsRepo`, both backends)

New row types `ResidentRow`, `ResidentMemoryRow`, `ResidentChannelRow`,
`ResidentMessageRow`, `ResidentAlarmRow` in `types.ts`. Methods (async, like
everything else on the interface):

```ts
// Roster
listResidents(): Promise<ResidentRow[]>;
upsertResident(row: ResidentRow): Promise<void>;
deleteResident(id: string): Promise<void>;          // cascades memories+alarms; messages kept (history)
// Memories
listResidentMemories(agentId: string): Promise<ResidentMemoryRow[]>;
upsertResidentMemory(row: ResidentMemoryRow): Promise<void>;   // remember(key)
deleteResidentMemory(agentId: string, key: string): Promise<void>; // forget(key)
setResidentMemories(agentId: string, rows: ResidentMemoryRow[]): Promise<void>; // UI replace-all
// Channels + log
listResidentChannels(): Promise<ResidentChannelRow[]>;
upsertResidentChannel(row: ResidentChannelRow): Promise<void>;
deleteResidentChannel(id: string): Promise<void>;   // also deletes its messages (today's behavior)
appendResidentMessage(row: Omit<ResidentMessageRow, 'id'>): Promise<number>;
listResidentMessagesAfter(id: number, limit: number): Promise<ResidentMessageRow[]>;
listResidentMessages(limit: number): Promise<ResidentMessageRow[]>;   // tail, for snapshot
pruneResidentMessages(keep: number): Promise<void>; // global bound, as today
// Alarms
listResidentAlarms(agentId?: string): Promise<ResidentAlarmRow[]>;
addResidentAlarm(row: Omit<ResidentAlarmRow, 'id'>): Promise<number>;
deleteResidentAlarm(id: number): Promise<void>;
```

SQLite writes bump `_change_seq` like every other write (self-notification
suppressed via the existing `noteLocalWrite` pattern in the launcher).

## 3. Launcher rewiring

**One-shot store→db migration** — shared pure-ish function (pattern:
`pages-relocation-migration.ts`) run at boot by both entry points
(`src/main/index.ts` after `openDatabase`, `src/server/managers.ts` per
tenant) before the manager constructs: read the six `resident*` electron-store
keys, insert rows (`morningHour` absent → `8`), then **delete the store keys**
(minus `residentMorningBeats`, which stays — it is delivery bookkeeping, not
world state). Idempotent by construction: keys absent → no-op. Store schema
(`types.ts` electron-store `schema`) drops the five migrated keys.

**`ResidentAgentManager` reads/writes the repo** instead of `store.get/set`.
It is already the I/O shell over pure `src/lib/resident-agent.ts` helpers, so
the pure layer is untouched; the shell's accessors become async repo calls.
Message-log bounding moves from slice-on-write to `pruneResidentMessages`
after append. The manager gains a `repo: IProjectsRepo` dep in both
registration sites.

**Renderer keeps its mirrors.** `buildStoreSnapshot()` (`db-store-bridge.ts`)
now assembles `residentAgents` / `residentMemories` / `residentChannels` /
`residentChannelDefs` / `residentAlarms` from the repo (row↔model mapping
lives in the bridge like every other entity). The `StoreData` keys remain as
**read-only snapshot mirrors** — the Residents tab and `resident:*` IPC
surface don't change shape; writes already flow exclusively through
`resident:*` handlers, which now hit the repo.

## 4. Residents as principals

**Principal id format: `agent:<rosterId>`** — same namespace as the process
id, collision-free with human principal ids (AAD oids / emails), string-typed
everywhere `assignee`/principal already is. `src/lib/resident-agent.ts` gains
`residentPrincipalId(id)` / `parseResidentPrincipal(p)` helpers; nothing
parses the prefix ad hoc.

**Directory.** `omni-projects`' `list_team_members` returns the union of
human members (context callback, cloud-only as today) and residents read
straight from the repo — which the stdio cli now has. Resident entries:
`{ user_id: 'agent:<id>', display_name: name, role: 'agent' }` (only
`enabled` residents). Local single-user mode thus goes from an empty roster
to "your agents."

**Session identity.** Two carriers, one resolution:

- _Local/stdio:_ the managed `mcp.json` is global (one `OMNI_CONFIG_DIR`), so
  identity rides **per-process env**: `ProcessManager` sets
  `OMNI_PROJECTS_PRINCIPAL=agent:<id>` in the spawn env when the process id
  is `agent:<id>` (the env propagates from `omni serve` to the stdio MCP
  child). `cli.ts` reads it and passes
  `{ getCurrentPrincipal: async () => env value ?? null }` to `createServer`.
- _Cloud/HTTP:_ `RuntimeTokenClaims` gains optional `aid` (resident id);
  minted when the server launches a resident's process. `mcp-http.ts` resolves
  the principal as `aid ? 'agent:'+aid : principalId`.

`get_current_principal` therefore answers correctly in all four quadrants
(local/cloud × user-session/resident-session); user sessions keep today's
behavior (`null` locally, user principal in cloud).

**Comment attribution.** `add_ticket_comment` keeps its optional
`author` enum, but when the session principal is a resident the server
**stamps `author` with the principal string**, ignoring the param (the DB
column is already a plain string). `TicketDiscussion` renders authors:
`agent:<id>` → resident display name (lookup via the `residentAgents`
mirror, falling back to the raw id), `'agent'` → today's generic agent
treatment, else human.

## 5. Assignment: roster + wakeup

**AssigneePicker** adds an "Agents" section under the human members list,
sourced from the `residentAgents` snapshot mirror (enabled only), assigning
`agent:<id>`. Current-assignee label resolution checks residents before
falling back to the raw id. `AssigneeFilter` gets the same source.

**Wakeup.** New `ResidentEvent` kind `'assignment'`, member of
`WAKE_NOW_KINDS`, ping line rendered from `detail` ("You were assigned
ticket `<id>` — _<title>_ in _<project>_"). Wiring: both entry points pass
an `onAssign(assignee, ticket)` observer into `ProjectManager` (the hook
already exists for cloud member notification at the `assignTicket`
chokepoint); when `parseResidentPrincipal(assignee)` matches a roster member,
call `residentAgentManager.deliverAssignment(id, ticket)`. Self/human/unknown
assignees are untouched. No un-assignment event (silence is fine; the agent
reads live state).

**WIP interaction (intentional):** `SupervisorOrchestrator` counts per-user
WIP by `assignee === principal`, so agent-assigned tickets stop counting
against the assigning user's WIP — correct, since the agent is the one
working them.

## 6. Explicitly out of scope (follow-ons)

- **Channel/memory MCP tools** (agents reading `#team` via tools, cross-agent
  DM tools): the data fold makes these possible; exposure is a separate
  surface decision.
- **Renaming `omni-projects`**: touches tuple-keyed approval grants and
  `safe_mcp_tools` lists across omniagents + launcher; do it (if at all) as
  its own lockstep change after this lands.
- **Cursors / urges / DM budgets / morning beats** stay manager-side; they
  are runtime, not world state.
- Resident-authored inbox items / tickets `created_by` attribution beyond
  comments — needs a `created_by` column decision across all entities; defer.

- **Identity**: mcp smoke test — `OMNI_PROJECTS_PRINCIPAL=agent:x` →

  `aid` resolve to `agent:<aid>`; without `aid` unchanged.

  writes `agent:<id>`; TicketDiscussion resolves `agent:<id>` to the display
  name.

## 8. Rollout slices

1. **Schema + repo** (projects-db only, both backends; no behavior change).
2. **Fold**: boot migration, manager on repo, snapshot mirrors from repo,
   store schema key removal. Residents tab works identically.
3. **Principals**: env + token carriers, cli context, directory merge,
   comment stamping.
4. **Assignment**: picker sections, `assignment` event, `onAssign` wiring.

Slices 1–2 land together or apart; 3 and 4 each depend only on 1–2.

## Assumptions

- `agent:<id>` as the principal string (mirrors the process-id convention);
  no separate principals table — the roster row _is_ the principal record.
- Deleting a resident keeps its messages in the log (history is a record) and
  leaves any `assignee: agent:<id>` pointers dangling; pickers fall back to
  rendering the raw id. No tombstones.
- `residentMorningBeats` remains an electron-store key (delivery state).
- The message log keeps a single global bound (today's behavior), not
  per-channel bounds.
- Server mode's per-tenant `ResidentAgentManager` picks up cloud parity
  automatically via the tenant repo; no new server wiring beyond the
  migration call and the repo dep.
- v1 makes no schema room for per-agent API keys/secrets; identity is
  launcher-asserted (env/token), not credentialed.
